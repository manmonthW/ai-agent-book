# 蓝皮书写作风格规范

## 1. 基本原则

- 先回答“为什么和怎么选”，再解释“怎么实现”。
- 先写框架无关契约，再写具体 SDK 案例。
- 区分事实、实验观察、工程建议、作者判断和未来预测。
- 不用复杂术语替代可验证的机制。
- 不把模型生成的“完成”当作任务完成证据。

## 2. 每章固定结构

1. 本章回答的三个问题
2. 5 分钟速读：一页结论
3. 核心概念与边界
4. 架构与运行机制
5. 设计选择和取舍
6. 代表案例
7. 常见失败模式
8. 生产建议
9. 实验与证据
10. 决策/检查清单
11. 知识检查
12. 延伸阅读

## 3. 表达规范

- 一个小节回答一个主要问题。
- 段落优先采用“问题 → 原理 → 架构 → 案例 → 风险 → 建议”。
- 首次出现术语时给中文、英文和缩写。
- 代码只保留解释机制所需的最小部分。
- 长日志、安装步骤、算法推导进入实践册或附录。
- 产品能力必须注明版本或 `as of` 日期。

## 4. 信息框

- **蓝皮书结论**：高置信、跨框架结论。
- **架构决策**：适用条件、替代方案和取舍。
- **风险警示**：生产影响和控制措施。
- **实验结论**：实验变量、指标和证据等级。
- **厂商案例**：特定产品或 SDK，不外推为普遍结论。
- **技术深潜**：跳过后不影响主线。

## 5. 禁止模式

- 未注明来源的精确数字。
- 用“业界普遍”“显著提升”等措辞但无证据。
- 将 Tool Calling、MCP、A2A、Skill 混为一谈。
- 将 Memory 当作权威数据库。
- 将 LLM Judge 当作权限或事实裁判。
- 仅因角色名称不同就推荐多 Agent。
