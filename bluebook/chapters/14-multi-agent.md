# 第14章　多Agent：何时值得复杂化

> 状态：Release Candidate 1  
> 核心问题：如何用多个独立Agent获得真实信息或控制增量，而不是只增加角色和Token。

## 本章回答的三个问题

1. 多Agent何时优于单Agent或Skill？
2. 共享/独立上下文和不同拓扑如何选择？
3. 数据平面、控制平面、预算和失败恢复如何设计？

## 5分钟速读

- 多Agent需要准入理由：新信息、并行覆盖、上下文隔离、独立权限或真实异步委派。
- 角色名称不同不等于独立能力；同模型同上下文讨论可能只重复错误。
- 知识和流程差异优先用Skill，有限子任务优先Manager-as-tools。
- 共享上下文信息损失少但膨胀快；独立上下文隔离好但需显式通信。
- Artifact经共享工作区交换，控制通过消息、状态、取消和调度完成。
- Worker有私有工作区和预算，返回结构化结果，不返回全部轨迹。
- Reviewer必须读取测试、截图、外部事实等独立证据。
- 多Agent必须与等预算单Agent基线比较。

## 一、准入测试

至少满足一项：

- 独立并行研究显著降低延迟或扩大搜索覆盖；
- 子问题超出单一上下文，隔离减少污染；
- 身份或权限必须分离；
- 专家必须直接接管持续交互；
- Artifact所有权和异步委派是真实需求。

以下不成立：框架支持、角色更像团队、多个Agent“应该更聪明”。

## 二、先考虑更简单方案

```text
同一Agent加载Skill
→ 调用专业工具
→ Manager委派有界子任务
→ Handoff持续交互
→ 去中心化协作
```

从左到右复杂度增加。每次升级都需评估证据。

## 三、上下文共享

### 共享上下文

后续角色继承完整轨迹。优点是细节不丢；缺点是上下文膨胀、权限边界弱和角色干扰。

适合短流程阶段切换。若角色差异只在规程和风格，可用Skill保持稳定前缀；若权限和工具必须隔离，使用独立Agent。

### 独立上下文

每个Agent拥有自己的轨迹和状态，通过消息或Artifact交流。优点是隔离、并行和模块化；代价是信息同步、接口和调试复杂。

## 四、三种拓扑

### Peer

少量Agent对等迭代，例如Proposer–Reviewer。需要独立证据和最大轮数。

### Manager

Manager拆分、分配预算、收集结果和解决冲突。适合最终答案需要一个Owner。

### Decentralized

Agent通过消息和协议自主协作。适合组织边界和动态发现，但身份、合同、一致性和故障处理最复杂。

## 五、数据平面

虚拟文件系统可分：

```text
/agents/{id}/scratch     # 私有临时区
/workspace/shared        # 任务共享产物
/mnt/external            # 授权外部资源
/system/skills           # 只读系统资源
```

传递Artifact URI、Hash、Schema和权限，不把大型内容复制进消息。共享写入使用版本、锁或Worktree，避免覆盖。

## 六、控制平面

核心原语：

- `spawn_agent`：创建并分配任务、身份、工具和预算；
- `send_message`：结构化消息；
- `publish_status`：运行中、等待、完成、失败；
- `cancel_agent`：优雅取消并级联；
- `list_agents`：发现和诊断；
- `collect_result`：结构化结果与Artifact；
- Scheduler：并发、优先级、抢占和费用。

消息信封：

```yaml
message_id: msg_123
sender: research_agent_1
recipient: manager
run_id: run_456
type: result
payload_ref: artifact://runs/run_456/source-a.json
schema: research-result-v2
created_at: ...
```

## 七、Proposer–Reviewer

有效循环：

```text
Proposer候选
→ 执行/渲染/查询
→ Reviewer读取独立证据
→ 结构化缺口
→ 修复
→ 独立Verifier终止
```

无效循环：多个Agent只看同一候选文本并互相表达意见，没有环境反馈。

## 八、预算与调度

每个Worker设置：

- 模型路由；
- 最大步骤、Token、时间和费用；
- 工具范围；
- 任务优先级；
- 取消和结果截止时间。

Manager根据任务复杂度分配预算，但Runtime执行硬上限。并发达到上限时排队；一个Worker找到充分答案后，取消冗余探索。

## 九、结果合并

合并契约包括：

- Schema一致；
- 来源和证据；
- 冲突事实显式保留；
- 缺失和失败Worker；
- 去重；
- 责任Owner；
- 最终验证。

不要用另一个模型无依据地“综合”互相冲突的事实，应回到来源或请求人工裁决。

## 十、A2A与跨组织协作

A2A可标准化能力发现、任务、消息和状态，但仍需：

- 双方身份与认证；
- 授权和目的限制；
- 数据合同和保留政策；
- 消息签名和重放保护；
- SLA、费用和责任；
- 不可信输出验证。

协议互操作不等于业务信任。

## 十一、失败模式

| 失败 | 控制 |
|---|---|
| 角色多但信息相同 | 新信息准入测试 |
| Context复制爆炸 | 独立上下文和Artifact引用 |
| Worker权限过宽 | 独立身份与最小工具 |
| 共享文件冲突 | 私有工作区、版本合并 |
| Manager无限委派 | 深度、并发和成本预算 |
| Reviewer复述意见 | 独立测试/渲染/事实证据 |
| 子Agent成为孤儿 | 生命周期级联取消 |
| 冲突被静默综合 | 来源保留和显式裁决 |

## 十二、评估

与等预算单Agent比较：

- 成功率和覆盖；
- 延迟；
- Token和费用；
- 冲突与合并错误；
- 上下文污染；
- 权限违规；
- 取消和恢复；
- Artifact质量。

只有增量价值覆盖复杂度和成本时才保留多Agent。
