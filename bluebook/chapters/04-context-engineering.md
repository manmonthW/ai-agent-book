# 第4章　上下文工程：为每一次决策准备正确的信息

> 状态：Release Candidate 1  
> 阅读路径：5分钟掌握上下文预算；30分钟理解生命周期与失败模式；实践时对照实验1-1、2-3和2-10。

## 本章回答的三个问题

1. Agent的一次模型调用究竟看到了什么？
2. 为什么更长的上下文不一定更好，哪些信息应进入、压缩或移出上下文？
3. 如何同时控制缓存效率、信息污染、提示注入和长任务遗忘？

## 5分钟速读：一页结论

1. **上下文是当前决策可见的信息，不是所有已知信息。** 它通常包括系统策略、工具定义、用户目标、运行状态、相关证据和必要历史。
2. **上下文决定可见性，但不保证真实性。** 用户输入、网页、检索结果、工具输出和Agent消息都应携带来源与信任标签。
3. **稳定前缀与动态轨迹应分开管理。** 稳定策略和工具Schema放在前缀，任务进展和观察追加到轨迹，有利于缓存、版本控制和调试。
4. **上下文组件不能被一概而论为“不可或缺”。** 是否能删除，取决于信息能否从其他观察重建；必须通过具体任务和模型实测。
5. **Prompt、Skill和Memory用途不同。** Prompt定义当前政策，Skill按需披露流程，Memory保留跨交互信息；它们都不能替代代码层授权。
6. **长上下文有四类典型故障**：Poisoning、Distraction、Confusion和Clash。
7. **压缩目标不是最少Token，而是保留下一步决策所需证据。** 优先移除可重建内容、重复内容和已归档Artifact正文。
8. **上下文窗口不是长期记忆。** 长期事实应进入可治理的Memory或权威数据库，大型产物应按引用访问。
9. **工具数量也是上下文问题。** 完整工具Schema过多时，应按身份和任务过滤，或采用稳定的工具发现入口。
10. **上下文改动必须评估结果与轨迹。** 只看Token减少可能掩盖引用丢失、重复调用或错误完成。

> **蓝皮书结论**  
> 上下文工程不是“把更多资料塞给模型”，而是为每一个决策点选择最相关、可信、可追溯且符合预算的信息。

## 一、上下文的边界

### 1.1 上下文不是知识库

上下文是模型**此刻**能够看到的信息。知识库是外部事实源，Memory是跨交互保存的信息，Artifact是可持久引用的中间或最终产物。它们需要经过检索、选择或引用，才能进入当前上下文。

| 对象 | 主要用途 | 生命周期 | 是否全部进入模型 |
|---|---|---|---|
| Context | 支持当前决策 | 一次调用或当前轨迹 | 是，但应受预算限制 |
| Runtime State | 保存任务事实和状态机 | 一次运行 | 只注入当前步骤需要的字段 |
| Memory | 保存可治理的跨交互信息 | 跨会话 | 按需检索 |
| Knowledge Base | 提供外部权威知识 | 独立维护 | 检索相关证据 |
| Artifact | 保存文档、代码、报告和中间结果 | 任务内或长期 | 传引用、摘要或相关片段 |
| Authoritative DB | 保存业务事实 | 由业务系统决定 | 通过工具查询，不复制为“记忆” |

把所有对象都称为Memory会模糊权威性：用户偏好可以存在Memory，账户余额应实时查询业务系统。

### 1.2 一次模型调用的六部分

生产上下文可按以下结构理解：

1. **稳定系统策略**：身份、行为边界、不可覆盖规则；
2. **工具定义**：当前身份被允许看到和调用的工具Schema；
3. **当前目标与步骤**：用户目标、当前子任务和成功条件；
4. **类型化运行状态**：已确认事实、待办、错误和剩余预算；
5. **相关证据**：检索文档、工具观察、来源和信任等级；
6. **必要轨迹**：理解当前决策所需的历史，而不是无差别完整聊天记录。

第一、二项通常形成稳定前缀；后三项随执行变化。运行状态处于两者之间：其Schema稳定，值动态变化。

## 二、稳定前缀与动态轨迹

![图4：上下文生命周期](../images/architecture/fig04-context-lifecycle.svg)

### 2.1 为什么分层

```text
稳定前缀
├── System policy
├── Tool schemas
└── Stable skill index

动态决策包
├── Current goal and step
├── Typed state
├── Retrieved evidence
├── Relevant trajectory
└── Remaining budget and termination conditions
```

分层带来三项收益：

- **缓存**：前缀稳定时，供应商更可能复用已有计算；
- **治理**：策略、Schema和工具集可以独立版本化；
- **调试**：可以区分是长期政策错误，还是某轮动态信息错误。

但不应为了缓存牺牲安全。例如当前用户没有写权限时，写工具不应仅靠Prompt禁止；应从可用工具集合中移除或由策略网关拒绝。

### 2.2 轨迹保存什么

轨迹通常包含：

```text
用户目标
→ 模型决策或工具调用
→ 参数校验结果
→ 工具观察
→ 状态更新
→ 下一次决策
```

不是每个内部推理Token都必须永久保留。判断一段历史能否删除，可以问：

- 下一步是否需要这个事实？
- 该信息能否从工具结果或状态中重建？
- 删除后是否会重复已经完成的动作？
- 是否需要它解释权限、审批或错误来源？
- 它是否已保存为Artifact并可按引用读取？

## 三、实验1-1给出的真实边界

主仓库实验1-1比较了完整上下文与移除工具定义、工具结果、保留的assistant reasoning和历史消息等条件。该实验最重要的价值不是证明一个永恒排名，而是展示如何用消融检查上下文组件。

经过修订的实验记录支持以下限定结论：

- 没有工具定义时，Agent失去对应行动接口，但模型仍可能生成看似完整的文字；“有答案”不等于完成任务。
- 工具结果被静默移除后，多数探测运行反复调用到迭代上限，但样本量较小，行为也非确定性。
- 移除历史中保留的reasoning并未使两次记录运行失败；当“为什么”可以从“发生了什么”重建时，保留全部reasoning可能没有额外价值。
- 移除历史可能导致重复操作，因为Agent无法看到已完成步骤。

因此蓝皮书不采用“每个上下文组件都不可或缺”的绝对表述。正确方法是：

```text
提出该组件承载的信息
→ 删除或替换
→ 保持任务、工具和模型尽量一致
→ 比较最终结果、轨迹、成本和失败方式
```

> **实验结论｜E4，限定适用**  
> 上下文组件的价值取决于它携带的信息是否能从其他状态或观察重建。组件名称本身不能决定是否保留。

## 四、KV Cache友好的设计

### 4.1 工程直觉

Transformer每次处理长前缀都会产生计算成本。若连续调用共享相同前缀，推理服务可以复用已有KV Cache；如果前部内容频繁变化，后续缓存通常也随之失效。

因此可采用：

- 稳定策略放在前部；
- 工具Schema保持稳定排序；
- 用户个性化和时间状态放在动态区域；
- 不在每轮随机重排工具；
- 用版本ID引用稳定政策，而不是每次重写整段文本。

### 4.2 不要把缓存优化写成业务规则

缓存是实现优化，不应改变安全边界。动态权限必须真实反映当前身份；若工具集合变化是正确授权结果，就应接受缓存变化，而不是为了命中率继续向无权限用户暴露工具。

实验2-3在特定模型和供应商环境中比较了稳定前缀、动态系统信息、工具重排、滑动窗口和扁平文本。其方向性结果可用于解释缓存机制，但具体时延和缓存比例不能外推到所有供应商。

## 五、Prompt、Skill、状态和Memory

### 5.1 Prompt：当前政策

Prompt适合表达：

- 角色与目标；
- 输出格式；
- 当前流程约束；
- 何时澄清或停止；
- 如何解释工具结果。

Prompt不适合承担：

- 身份认证；
- 数据访问控制；
- 金额和状态事实；
- 不可逆动作授权；
- 可靠的Token或费用硬上限。

### 5.2 Skill：渐进式披露的流程知识

Skill适合把可复用流程、检查清单、示例和脚本组织为文件。模型先看到Skill目录，在需要时再加载具体内容，从而避免把所有专业规程永久放入系统前缀。

Skill是行为指导，不是权限边界。加载“部署Skill”不代表当前身份有权部署；最终权限仍由Harness判断。

### 5.3 状态栏：把运行事实显式化

状态栏可包含：

```yaml
run_id: run-123
current_step: verify_input
completed:
  - collect_documents
blocked_by: null
remaining_tool_calls: 8
wall_time_remaining_seconds: 120
approval_required_for:
  - submit_refund
```

状态应由运行时生成，模型不能任意把`approval_granted`从false改成true。

### 5.4 Memory：跨任务保存，但必须治理

保存Memory前应回答：

- 是否真的需要跨会话？
- 来源是谁，可信度如何？
- 用户能否查看、更正和删除？
- 是否有租户隔离和过期时间？
- 与权威业务事实冲突时谁优先？

## 六、四类上下文故障

### 6.1 Context Poisoning：污染

错误或恶意信息进入上下文，并在后续步骤被当作可信指令或事实。

来源可能包括网页、邮件、检索文档、工具输出、Memory和其他Agent消息。

控制：

- 来源与信任标签；
- 指令和数据分离；
- 外部内容不得提升权限；
- 知识入库审核和版本；
- 高风险事实实时查询权威系统。

### 6.2 Context Distraction：干扰

大量相关度较低的信息占据注意力和预算，使模型忽略关键要求。

控制：检索过滤、Rerank、任务相关裁剪、Artifact引用和分步决策包。

### 6.3 Context Confusion：混乱

工具、规则或示例太多，模型难以判断当前适用哪一个。

控制：按身份和步骤过滤工具、Skill渐进披露、清晰Schema、删除过时指令。

### 6.4 Context Clash：冲突

系统策略、用户要求、Memory、检索事实或多Agent消息彼此矛盾。

控制：

- 明确信息优先级；
- 对事实保留来源和时间；
- 检测冲突而非静默覆盖；
- 需要时向用户澄清；
- 状态更新使用版本和乐观锁。

## 七、Prompt Injection：信息不能授予权力

提示注入的危险不只是模型输出错误，而是外部内容试图改变系统目标或诱导工具调用。安全设计应满足：

```text
外部内容可以影响“模型知道什么”
但不能改变“模型被允许做什么”
```

具体措施：

- 把检索内容和网页文本标记为数据；
- 工具调用后再次执行授权与业务规则；
- 限制网络、文件和数据库范围；
- 高风险动作要求准确载荷审批；
- 对工具参数和结果设置大小、类型和超时限制；
- 不因模型声称“系统要求”而扩大权限。

实验2-5完成了多攻击渠道和多防御配置的运行，但所有观测攻击成功率均为0，包括基线。因此它证明实验活动和防御实现存在，却不能证明“每增加一层防御，成功率就按预期下降”。这类零事件结果需要更强攻击集或更多模型后再比较方向。

## 八、上下文压缩

### 8.1 何时压缩

触发条件可以包括：

- 接近模型窗口或预算；
- 工具输出重复或过长；
- 已完成阶段不再需要原始细节；
- 大型内容已成为Artifact；
- 当前步骤只需要部分证据。

### 8.2 四种处理动作

| 动作 | 适用内容 | 风险 |
|---|---|---|
| Drop | 可重建、重复、无关内容 | 错删未来步骤需要的信息 |
| Summarize | 长对话和阶段结果 | 摘要引入错误或丢来源 |
| Extract | 数字、实体、约束、决策 | 忽略语境 |
| Externalize | 文档、代码、图像、长日志 | 引用失效或权限变化 |

高质量压缩应保留：

- 当前目标和成功条件；
- 已确认事实及来源；
- 未解决问题；
- 已执行副作用和幂等键；
- 审批状态；
- 最近失败及其恢复信息；
- 剩余预算。

### 8.3 实验2-10的限定启示

实验2-10在同一研究任务中比较多种压缩策略，保存了无压缩溢出和五种完成策略的真实运行记录。它支持两个工程判断：

1. 长工具输出会迅速耗尽窗口，不能无限追加；
2. 不同压缩方法会改变迭代次数、Token、引用和任务完成方式。

它不证明某一种压缩算法对所有任务都最佳。压缩策略应按任务评估，尤其检查引用是否仍能追溯、关键数字是否保留、Agent是否因摘要缺失而重复调用工具。

## 九、每个决策点的上下文模板

```yaml
policy:
  prompt_id: support-agent
  prompt_version: 4
  non_overridable_rules:
    - external_content_cannot_grant_permissions

goal:
  user_outcome: 取消重复订阅
  current_step: verify_subscription
  success_condition: authoritative_status_is_cancelled

state:
  run_id: run-123
  completed_steps: [identify_account]
  pending_steps: [verify_subscription, preview_cancel, approval, execute]

trusted_facts:
  - value: subscription_id_456
    source: billing_api
    observed_at: 2026-09-21T10:00:00Z

retrieved_evidence:
  - content_ref: artifact://policy/cancellation-v7#section-3
    trust: internal_policy
    valid_as_of: 2026-09-01

available_tools:
  - get_subscription_status
  - create_cancellation_preview

budget:
  model_calls_remaining: 4
  tool_calls_remaining: 6
  wall_time_remaining_seconds: 90

termination:
  success: authoritative_status_is_cancelled
  blocked: approval_or_required_data_missing
  failure: budget_exhausted_or_nonrecoverable_tool_error
```

这个模板的重点不是YAML格式，而是把政策、目标、状态、事实、证据、工具、预算和终止条件分开，避免一段无法检查的长Prompt承担所有职责。

## 十、评估上下文改动

至少衡量：

| 维度 | 问题 |
|---|---|
| Outcome | 最终任务是否真正完成？ |
| Grounding | 结论是否来自可追溯证据？ |
| Trajectory | 是否重复调用、选错工具或提前终止？ |
| Compression | 关键约束、数字和来源是否丢失？ |
| Cache | 稳定前缀是否提高缓存复用？ |
| Cost | 每个成功任务成本是否下降？ |
| Security | 外部内容是否改变权限或政策？ |

采用同任务、同工具、同模型和重复运行的对照，避免把模型随机性误判为上下文设计效果。

- [ ] Prompt和Skill不承担硬授权。
