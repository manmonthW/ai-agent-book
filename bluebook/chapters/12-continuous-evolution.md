# 第12章　从轨迹到持续进化

> 状态：Release Candidate 1  
> 核心问题：如何把已评价的运行经验变成下一版本能力，而不让错误经验污染系统。

## 本章回答的三个问题

1. 哪些运行轨迹值得学习，如何得到可靠学习信号？
2. 应更新知识、Prompt/Skill、程序/Harness还是模型参数？
3. 新版本如何验证、灰度、回滚并长期整理？

## 5分钟速读

- 轨迹只有在结果和过程被评价后才是学习资产。
- 学习信号来自环境结果、确定性过程规则和经校准Rubric。
- 优先更新最可控载体：知识 → Prompt/Skill → 程序/Harness → 参数。
- 不从单次失败直接生成永久规则；先聚类、复现和验证根因。
- 更新必须带来源、版本、适用范围、证据和过期条件。
- 新版本在隔离环境离线回放，经过Shadow、Canary和回滚门禁。
- 防止评估集泄漏、错误经验强化、规则无限堆积和版本不可解释。

## 一、闭环

```text
生产轨迹
→ 脱敏与采样
→ 结果/过程评价
→ 失败归因与聚类
→ 选择更新载体
→ 生成候选变更
→ 离线回放与对照
→ 灰度发布
→ 在线监控
→ 新失败回流
```

任何一步缺少来源和版本，都会使后续无法判断改动为何有效或失败。

## 二、学习信号

### 环境结果

测试、数据库状态、页面结果、支付回执和用户确认。最接近真实目标。

### 过程规则

例如必须先审批后支付、不得访问越权路径、必须引用来源。适合确定性检测。

### LLM Rubric

用于风格、完整性和开放任务质量。需要人工校准，不能决定事实和权限。

综合信号应区分：成功、部分成功、错误完成、正确拒绝、阻塞和系统故障。

## 三、失败归因

先找**第一个关键错误**：

- 缺少上下文；
- 检索错误；
- 工具选择或参数错误；
- 模型推理错误；
- Harness状态或重试错误；
- 政策和权限错误；
- 验证器错误；
- 环境不可用。

最终错误常是级联结果。只有根因可复现时才生成候选更新。

## 四、四种更新载体

### 4.1 知识

适合事实、政策和案例。要求来源、时效、权限和删除。

### 4.2 Prompt与Skill

适合可语言化流程、写作规则和检查清单。Skill便于按需披露，避免系统Prompt无限增长。

### 4.3 程序与Harness

适合确定性规则、校验、工具路由、状态机、权限和验证器。高风险不变量优先进入代码。

### 4.4 模型参数

适合难以显式表达、需要广泛泛化的高维能力。成本和验证要求最高。

选择顺序：

```text
能查权威源？更新知识
能清楚写成规程？更新Prompt/Skill
能确定性验证？更新程序/Harness
难以显式表达且有足够数据？考虑训练
```

## 五、候选变更生成

每个候选包含：

```yaml
change_id: skill-refund-clarification-v3
source_failures: [run_12, run_41, run_88]
root_cause: missing clarification before irreversible action
carrier: skill
scope: refund_agent
expected_effect: reduce_wrong_target_refunds
risks:
  - extra_turns
  - user_dropoff
rollback: skill-v2
expiry_review: 2026-12-01
```

不把生产原始对话直接拼进Prompt；先脱敏、归因和提炼。

## 六、验证

- 建立最小回归任务；
- 在完整私有集离线回放；
- 比较目标指标和副作用；
- 检查其他任务回归；
- 记录模型、Prompt、工具和环境；
- 新旧版本使用相同预算；
- 达不到最小增益则不发布。

## 七、发布与回滚

```text
离线 → Shadow → Canary → 有界放量 → 全量
```

候选在Shadow中读取真实输入但不产生真实副作用。Canary限制租户、工具和影响等级。出现安全违规、成功率下降或成本超阈值立即回滚。

## 八、长期整理

持续更新会造成：

- Prompt和Skill规则堆积；
- 知识重复和冲突；
- 旧评估任务失效；
- 多个临时Harness补丁互相作用；
- 模型、规则和数据版本无法解释。

定期执行：去重、合并、过期、冲突检查、回归测试和所有权审查。

## 九、经验污染防护

- 只学习已验证轨迹；
- 对恶意输入和攻击轨迹隔离；
- 不把用户私有数据跨租户复用；
- 区分模型失败与环境故障；
- 防止测试答案进入训练数据；
- 保留未修改原始证据和变更链；
- 支持用户删除和法规保留策略。

## 十、常见失败模式

| 失败 | 控制 |
|---|---|
| 单次失败生成永久规则 | 聚类、复现、最小样本门槛 |
| Prompt无限增长 | Skill化、程序化、定期整理 |
| 把环境故障归因模型 | 错误分类和首错定位 |
| 只优化目标指标 | 检查成本、安全和回归 |
| 新版本无回滚 | 不可变版本和渐进发布 |
| 从攻击内容学习 | 隔离和信任标记 |
| 评估集泄漏 | 私有保留集和数据治理 |

## 十一、检查清单

- [ ] 轨迹有结果和过程评价。
- [ ] 首个关键错误可定位。
- [ ] 更新载体选择有理由。
- [ ] 变更带来源、范围、风险和回滚。
- [ ] 离线对照使用相同预算。
- [ ] 检查质量、成本、安全和回归。
- [ ] 发布渐进且可回滚。
- [ ] 经验脱敏、隔离并可删除。
- [ ] 定期清理规则和知识债务。

## 知识检查

1. 为什么运行轨迹本身不等于训练数据？
2. 如何选择四种更新载体？
3. 为什么应定位首个关键错误？
4. Shadow发布如何避免真实副作用？
5. 规则持续累积会产生什么问题？
